# .NET Code Indexer: Development Plan

A command-line tool that uses Roslyn to analyze .NET codebases and writes a queryable index to a SQLite
database. It plays the role of a **language server for AI agents**: instead of `grep`, an agent asks
precise questions (where is this defined, who references it, who calls it, what implements it) and gets
small, structured, trustworthy answers.

The indexer is a **standalone, general-purpose code-intelligence tool**. It knows nothing about any
consumer (workflow engines, mocking, personas). Consumers build on its queries.

Status: **Revised plan (2026-10-24), after a code review. All phases (A to G) are done.** Phases 0-3 of the first plan produced a working
skeleton (42 tests pass) but the extraction and storage layers have correctness gaps that defeat the
purpose (section 7). The revised phases fix those before adding features.

---

## 1. Goals and non-goals

### Goals
- Answer the questions an agent would otherwise use `grep` for, **correctly**: definition, references,
  implementations, incoming/outgoing calls, type hierarchy, file outline, and symbol search.
- Be precise about identity: overloads, generics, partial classes, nested types, and same-named symbols in
  different projects are distinct symbols, and every answer says which one it means.
- Return small structured JSON by default (limits, truncation flags, staleness), cheap for an LLM to read.
- Include **external symbols** (framework and NuGet APIs the code calls) so "who calls `X`?" works for
  library APIs too, not only code in the solution.
- Run locally on Windows from PowerShell with no network access; incremental re-indexing later.

### Non-goals
- Anything specific to a consumer or domain: remote-operation detection, mock generation, workflow
  tooling, persona integration. (See "Consumer-layer ideas" at the end.)
- Languages other than C#/VB.NET; a GUI; IDE integration; replacing the compiler.
- Cross-repository indexing (a possible later phase).

### How it maps to LSP

| LSP request | Command | Notes |
|---|---|---|
| `workspace/symbol` | `find-symbol`, `search` | Name and full-text search |
| `textDocument/documentSymbol` | `outline` | Members of a file or type |
| `textDocument/definition` | `definition` | By selector or `file:line:col` |
| `textDocument/references` | `refs` | With reference kinds (call, read, write, type-use, ...) |
| `textDocument/implementation` | `implementations` | Interface/abstract members and types |
| `callHierarchy/incomingCalls` | `callers` | With call-site lines; can follow dispatch |
| `callHierarchy/outgoingCalls` | `callees` | With call-site lines |
| `typeHierarchy/*` | `hierarchy` | Supertypes and subtypes |
| `textDocument/hover` | `show` | Signature, docs, optional source |

## 2. Key decisions

| Topic | Decision | Why |
|---|---|---|
| Runtime | .NET console app, later `dotnet tool` | Matches the stack; runs from PowerShell |
| Analysis | Roslyn `MSBuildWorkspace` + `Microsoft.Build.Locator` | Full semantic model |
| Storage | SQLite (`Microsoft.Data.Sqlite`) with FTS5 | Single file, zero setup, easy to inspect |
| Interface | CLI subcommands, JSON by default, `--format table` for humans | Cheap for agents to parse |
| Index location | One database **per solution/project**, outside the SDK fork, selected by `--db` or `--solution` via a catalog. `.codeindex\` and `*.db` git-ignored. | Disposable; never modifies the code under analysis |
| Restore | Precondition run by the user; the indexer detects missing `obj\project.assets.json` and says how to fix it | Keeps the tool read-only |
| **Symbol identity (new)** | Every symbol has a stable `key` = `<assembly name>\|<Roslyn documentation-comment ID>` (for example `SimpleLib\|M:SimpleLib.Calculator.Add(System.Int32,System.Int32)`). The key is unique in the database. All internal links use integer ids; all external references use the key. | Names are not identity: overloads, generics, and same-named types collide on name strings |
| **Multiple locations (new)** | A symbol has 1..n rows in `symbol_locations` (partial classes, partial methods). | Partial classes are central to the Google SDK |
| **Rebuild semantics (new)** | `index` writes a fresh database each run (build to a temp file, then replace). Incremental updates arrive in Phase F. | Re-running currently duplicates every row (finding F2) |
| **Query selectors (new)** | Every symbol-taking command accepts one of: `--id N`, `--key K`, `file:line:col`, or a name. A name matching several symbols returns a **candidates list** (with ids and keys), never an arbitrary first hit. | Agents must be able to disambiguate |
| Paths | Stored and emitted relative to the repo root with `/` separators | Portable, stable for agents |
| Staleness | Per-file content hash recorded; every query compares and sets `stale` | An outdated index must never be trusted silently |
| Tests | xUnit, with a rich fixture solution and tests that assert real results | The current fixture cannot exercise most hard cases (finding F12) |

Naming is a placeholder: working name **`codeindex`**.

## 3. Architecture

```
 solution/projects ──► Loader ──► Extractors ──► Writer ──► SQLite index.db
                                                                │
 Agent ──► CLI query commands ──► Query layer (SQL + FTS5) ──► JSON
```

- **Loader:** opens a `.sln`/`.slnx`/`.csproj`, selects one Roslyn project per project file (one TFM),
  reports load failures as diagnostics.
- **Extractors:** `SymbolExtractor` (declarations, one pass over `INamedTypeSymbol`/members per assembly,
  not per syntax node) and `ReferenceExtractor` (walks every identifier/name node in each syntax tree,
  resolves it, attributes it to the enclosing member). Each is a separate class.
- **Writer:** bulk inserts with prepared, reused commands inside one transaction.
- **Query layer:** parameterized SQL plus FTS5, returning compact DTOs.
- **CLI:** thin layer over the query layer.
- **Optional later:** a long-lived `serve` mode (JSON over stdio) to avoid per-call process startup, if
  agent usage shows it matters. The query layer is already a library, so this is a thin addition.

Projects: `CodeIndexer.Core`, `CodeIndexer.Cli`, `CodeIndexer.Tests`.

## 4. Schema (revision 3)

Every schema change bumps `schema_version` in `meta`.

| Table | Purpose | Key columns |
|---|---|---|
| `meta` | Schema version, index time, tool version, repo root, git commit | key, value |
| `solutions`, `solution_projects` | The solution(s) this database was built from | as before |
| `projects` | One row per project | id, name, path (**UNIQUE**), target_frameworks, indexed_tfm, language, is_external |
| `files` | One row per source file | id, project_id, path (**UNIQUE with project_id**), content_hash, line_count, is_generated |
| `symbols` | Types, members, **and external stubs** | id, **key (UNIQUE)**, kind, name, full_name, container_id (**populated**), signature, accessibility, doc_summary, is_generated, **is_external**, assembly |
| `symbol_locations` | Where a symbol is declared | symbol_id, file_id, start_line, start_col, end_line, end_col, is_primary |
| `symbol_references` | Every resolved use of a symbol | symbol_id, file_id, line, col, kind, **enclosing_symbol_id** |
| `edges` | Typed relationships | from_symbol_id, to_symbol_id, kind (`inherits`, `implements`, `overrides`, `creates`, `calls`) |
| `diagnostics` | Load and index problems (**actually written**) | severity, message, project_id, file_id |
| `symbols_fts` | FTS5 over names, signatures, docs | external-content table, rebuilt with the `'rebuild'` command |

Reference kinds: `call`, `use` (method group), `read`, `write`, `type-use`, `create`, `inherit`, `implement`,
`attribute`, `typeof`, `nameof`.

Indexes: unique keys above, plus `symbols(name)`, `symbols(full_name)`, `symbol_references(symbol_id)`,
`symbol_references(file_id, line)`, `symbol_references(enclosing_symbol_id)`, `edges` both directions,
`symbol_locations(file_id, start_line)`.

**Solution awareness across databases** stays as designed: every response carries solution name, path, and
indexed commit; a `catalog.db` lists every built database; `list`, `resolve`, and `--solution <name>`
select the right one.

### Phase C: Extraction rewrite (done 2026-10-24)
**Outcome:** the index answers references and call hierarchy correctly. Schema version 4. Suite: 163 passing,
0 skipped (all 14 pending tests promoted).
- [x] **Declarations (F3, F4, F17):** `SymbolExtractor` walks the compilation's declared symbols instead of syntax
      nodes. One row per symbol with a `symbol_locations` row per declaration, so a partial type is one symbol
      with several locations (the hand-written one is primary). Namespaces (shared across projects, no file),
      types including delegates (`delegate` kind), and all members are indexed; `container_id` is populated;
      accessors and implicitly declared members are not symbols of their own.
- [x] **References (F5, F7):** `ReferenceExtractor` resolves every simple name, object creation, constructor
      initializer, and indexer access in every document. Constructed generics map to their definition and reduced
      extension-method calls map to the declared static method. Each reference records its kind and the
      `enclosing_symbol_id` (lambdas and local functions belong to their containing member; property initializers
      and accessors belong to the property; field initializers to the field).
      Kinds: `call`, `use` (method group), `read`, `write` (compound assignment and `++` record both),
      `type-use`, `create`, `inherit`, `implement`, `attribute`, `typeof`, `nameof`.
- [x] **Edges (F6):** `inherits`/`implements` (type level, skipping implicit `object`/`ValueType`/`Enum`/delegate
      bases), `overrides` (methods, properties, events), member-level `implements` (implicit, via
      `FindImplementationForInterfaceMember`, and explicit), `calls` (including `: this(...)`/`: base(...)`),
      `creates` (to the constructor when declared, otherwise the type; includes target-typed `new()` and field
      initializers). A call to an interface or abstract member is recorded against that member, and the member
      `implements`/`overrides` edges let Phase D expand it to concrete targets.
- [x] **External symbols (F8):** symbols used but not declared in an indexed project (framework, NuGet, excluded
      projects) get stub rows (`is_external = 1`, no file, assembly recorded, container type stubbed too), so
      "who calls `HttpClient.GetStringAsync`?" works. Stubs are created only for symbols that are referenced.
- [x] **Generated detection (F20):** `*Grpc.cs`, `*.g.cs`, `*.g.i.cs`, `*.generated.cs`, `*.Designer.cs`, and an
      `<auto-generated>` header; a partial symbol is generated only if its primary location is.
- [x] **Memory/async:** no sync-over-async; symbols for a project are written as soon as that project is walked.
      (Compilations are still held for pass 2; measure in Phase E.)
- [x] Non-C# projects get a diagnostic and are skipped instead of failing.
- Query shield: the Phase 3 queries look symbols up with `is_external = 0 AND kind <> 'namespace'` so a name like
  `Add` cannot resolve to `List<T>.Add`. Phase D replaces name lookups with selectors.
- Known limits (carry into Phase D/E): user-defined operators, implicit conversions, `foreach`/`await` pattern
  calls, and deconstruction are not recorded as references; ambiguous overload resolution with several candidates
  records nothing; generated build files (`AssemblyInfo`) contribute attribute references to framework types, so
  queries should exclude generated files by default; `find-symbol`/`outline`/`search` still join to files, so
  namespaces and external stubs are invisible to them until Phase D surfaces them.

### Phase D: Query layer and CLI (done 2026-10-24)
**Outcome:** commands an agent can chain without ambiguity. Schema version 5. Suite: 233 passing.
The full response shapes are in `docs\code-indexer-output-contract.md`.
- [x] **Selectors:** every symbol-taking command accepts `--id`, `--key` (or a bare documentation id), a
      `file:line[:col]` position, or a name (full name, simple name, `Container.Member`, generic arguments ignored,
      `--kind` to narrow). A name matching several symbols returns `candidates` (with ids and keys) and a warning
      instead of an arbitrary first hit; hand-written beats generated, indexed beats external. Every symbol
      payload carries `id`, `key`, and `is_external`.
- [x] **`definition` and `at`:** `definition` lists every declaration location (a partial type has one per part);
      `at file:line[:col]` returns the symbol used at a position (with reference kind and enclosing member), else the
      innermost declaration containing it. References now store the token length so a column can be matched.
- [x] **`refs`:** `--ref-kind`, `--file`, `--project`, `--context` (source line), `--group-by file|member|kind`,
      limit/offset with `total_matches`; references in generated files are hidden by default with a count.
- [x] **`callers`/`callees`:** call sites per node, `--depth` (0 = unlimited; was returning nothing), `truncated`,
      `--through-dispatch` (callers of an override see calls made via its interface and base members; callees of a
      call to an interface member list the implementers), `--include-creates`, `--include-external`,
      `--exclude-generated`. Property/field/event "callers" return a hint to use `refs`. (F18)
- [x] **`implementations` and `hierarchy`:** works for types and for members (implements/overrides), direct or
      `--transitive`; hierarchy has explicit `supertypes` and `subtypes` trees, shows external supertypes flagged as
      such, and takes `--direction`/`--depth`.
- [x] **`outline`:** a file outline nests symbols by container and places them by where they are declared in that
      file (a partial type lists only that part's members); a type outline lists its members.
- [x] **Staleness (F15):** computed on every query by comparing size and modification time with the file on disk and
      hashing only on a mismatch; `stale`, `stale_files`, and a leading warning in every response. Index time
      records size and mtime and now hashes the file's bytes. Proven end to end by editing a file after indexing.
- [x] **`--format table` (F19):** implemented for every command (tables, key/value blocks, indented trees).
- [x] CLI: database defaults to the only indexed solution; exit codes 2 (no index) and 3 (query failed); a
      consistent selector option set; `search` and `find-symbol` can include generated and external symbols.
- [x] Output contract rewritten for all commands; tests for each command against the Semantics fixture, plus
      selector parsing, staleness (changed, touched-only, missing), JSON shape, and table output.
- Known limits: call sites on a node are those of the first path that reached it; name selectors for members of
  generic types need the type name without arguments (`Repository.Add`) and operators are not nameable;
  `find-symbol` substring matching can be broad on short names (use `--kind`/`--project`); staleness does not see
  files added after indexing.

### Phase F: Incremental indexing and freshness (done 2026-10-24)
**Outcome:** re-running `index` redoes only what a change affects, does nothing when nothing changed, and always
produces what a clean rebuild would. Schema version 6. Suite: 263 passing (about 2 minutes; the incremental scenario
test is most of it).

**The dependency rule.** The unit of work is the project. A project is redone when
1. one of its inputs changed: a source file (including generated ones under `obj\`), additional file or analyzer
   config, its project file, its restore output (`obj\project.assets.json`), or the set of `*.cs` files under its
   directory (an addition, deletion, or rename; a fingerprint of the sorted relative paths, not of the contents);
2. it was added to the solution; or
3. any project it references, directly or transitively, is redone, because what it binds to may have changed.
   Projects the filter excludes still count here: their inputs are tracked, and indexed projects that reference them
   are redone when they change.

Everything is rebuilt, rather than updated, when a build-wide file changed or appeared (`Directory.Build.props`,
`.targets`, `.rsp`, `Directory.Packages.props`, `global.json`, `nuget.config`), the project filter changed, the .NET SDK
changed, the tool version or schema differs, the index belongs to a different solution, the index file is unreadable, or
every indexed project would be redone anyway. `--full` forces a rebuild; `--dry-run` shows the plan and writes nothing.

- [x] **Inputs table:** at index time every input is recorded (path, kind, owner project, whether the owner is indexed,
      content hash, size, modification time), for all loaded projects including excluded ones, plus the solution and
      build-wide files. A file is re-read only when its size or modification time differs, and counts as changed only if
      its content does (saving without editing is not a change).
- [x] **Up to date without loading:** if no input changed, `index` reports it and exits without starting MSBuild:
      244 ms for Storage.V1, against 22 s to rebuild.
- [x] **Update in place, in one transaction:** the redone projects are deleted (foreign keys remove their files, symbols,
      locations, references, and edges) and written again by the same two passes a full build uses, resolving references
      into the kept projects through their existing symbol keys. Kept projects are untouched, symbol ids included (ids of
      redone projects are new; keys are always stable). A failure rolls back and leaves the index as it was.
      Orphans are collected afterwards: external stubs nothing points at, and namespaces nothing declares.
- [x] **Deleted, renamed, and added files and projects:** handled through the listing fingerprint, the source inputs, and
      the project list; a removed project's rows and inputs go. Project-file and restore changes redo the project.
- [x] **Staleness uses the same inputs (F15):** every query now also notices files added, deleted or renamed and changes
      to the solution and build-wide files, not only edits to indexed files; it ignores projects the filter excluded.
- [x] **Tests:** one long scenario applies a sequence of 16 steps to a throwaway copy of the `Incremental` fixture (Base, Mid
      uses Base, Leaf uses Mid, Solo uses nothing, Tests uses Base and is excluded) and, after each, compares the updated
      index with a clean rebuild of the same files: body edits, an API change at the start of the chain, an unchanged
      save, adding, deleting and renaming files, editing an excluded project and a project file, a dry run, adding and
      removing a project, a build-wide file appearing and disappearing, a filter change, a tool-version mismatch, and
      `--full`. It also asserts which projects were redone and kept, and that kept projects keep their symbol ids.
      Separate tests cover atomicity (an update sabotaged mid-way leaves the index identical, and the retry works), an
      old-schema and a corrupt index file, the planning rule, the input scanner, garbage collection, and a negative control
      showing the comparison fails for each kind of damage it covers.
- [x] **Verified on the Google fork** (read-only; the fork stayed clean), by making recorded inputs look changed in a copy
      of the Storage.V1 index and comparing each result with a full rebuild by an independent Python script (identical
      symbols, locations, references, edges, files, projects, diagnostics, inputs):

      | Change | Projects redone | Kept | Time |
      |---|---|---|---|
      | nothing | none (nothing loaded) | all | 0.24 s |
      | a ThroughputTool file | ThroughputTool | 4 | 9.6 s |
      | `StorageClient.cs` | Storage.V1, RetryConformanceTests, ThroughputTool | ClientTesting, PubSub.V1 | 14.1 s |
      | a file added/removed in PubSub.V1 | PubSub.V1, RetryConformanceTests | 3 | 20.3 s |
      | full rebuild | all | none | 21.9 s |

- Limits: any run that has to update still loads the whole solution with MSBuild (about 7.5 s here), which is why a leaf
  edit is 9.6 s rather than 2 s; a `Compile Include` that pulls in files from outside the project directory is tracked per
  file but a new such file is only noticed when the project file changes; installing a newer SDK when no `global.json`
  pins one is noticed only on the next run that loads the solution; `--watch` is not implemented (deferred, as the plan
  allowed): run `index` before a query, or rely on the `stale` flag.

### Phase G: Packaging and agent ergonomics (done 2026-10-24)
**Outcome:** installable, self-describing, and usable by an agent without a process start per lookup. Suite: 296 passing.
- [x] **`dotnet tool` package** (`CodeIndexer.Cli`, command `codeindex`, version from `<Version>` in `Directory.Build.props`;
      a test keeps it equal to the version stamped into indexes). `dotnet pack CodeIndexer.Cli -c Release` writes
      `artifacts\CodeIndexer.Cli.0.1.0.nupkg` (27 MB, almost all Roslyn). Verified by installing it into an empty tool path and
      indexing and querying from an unrelated directory (the MSBuild host files are in the package), and as a local tool
      (`dotnet new tool-manifest`, then `dotnet codeindex ...`). Not published anywhere.
- [x] **ReadyToRun:** a framework-dependent tool package cannot carry a ReadyToRun image, so it is JIT-compiled: about 265 ms
      per CLI call, of which .NET host start-up is about 158 ms. `dotnet publish CodeIndexer.Cli -r win-x64
      -p:PublishReadyToRun=true` gives about 215 ms for people who want it. This is the reason for the next item.
- [x] **Decision: an MCP server, not a custom `serve` protocol.** A persistent process turns a 265 ms call into a 4 ms one
      (measured through a real process over stdio: first call about 90 ms while JIT warms up, then 4 ms). Of the two forms
      considered, MCP is what agents already speak (Claude Code, Cursor, and others register a stdio server in one line),
      while a bespoke line protocol would need a client written for every use. `codeindex mcp [--db | --solution]` is
      read-only: 12 tools (`find_symbol`, `search`, `definition`, `show`, `outline`, `at`, `refs`, `callers`, `callees`,
      `implementations`, `hierarchy`, `index_info`) whose descriptions and argument schemas are written for a model; results
      are the same JSON as the command line, including `candidates` for an ambiguous name and `stale`; errors a model can act
      on (no index, missing argument, non-numeric id) are tool errors, not protocol errors; each call opens the index fresh so
      staleness is always current; optional `solution` selects among several indexes. It never writes the index.
      **Not done:** exercising it from a real Claude Code or Cursor session; it is tested with 24 in-process protocol tests
      (handshake and version negotiation, notifications, ids, errors, every tool) and one test that drives the real executable
      over stdin and stdout and checks nothing but JSON-RPC reaches stdout.
- [x] **`--help` for an LLM:** the program is named `codeindex` (it printed `CodeIndexer.Cli`); the root help states what the
      tool is for, a three-line workflow, how to name a symbol, and that an ambiguous name returns candidates; commands have
      one-line descriptions in a consistent voice; empty `[]` and `[default: False]` noise is gone; arguments that must be given
      (`find-symbol <name>`, `search <text>`, `at <position>`) are required, so a missing one is an error instead of an empty
      result; `index --db` says where the database is written.
- [x] **README** (`README.md`, also the package readme): what it answers, install, PowerShell quick start, command table, symbol
      selectors, freshness, agent setup with a suggested prompt, what to know before trusting a result, measured speed,
      development layout.
- [x] **CLI tests:** the command-line layer previously had none. Nine tests run the built executable: help text, per-command help,
      required-argument errors, exit code 2 with a message on stderr when there is no index, index then query then index again
      (up to date) then `--full --dry-run`, and a real MCP session.
- [x] **CI** (`.github\workflows\code-indexer.yml`, repository root): on changes to `project/code-indexer`, on Windows: build, test,
      pack, install the packed tool and run it, upload the test results and the `.nupkg`. **Not run on GitHub from here.** It
      parses as YAML and each command in it was run locally. The suite has only ever run on Windows.
- Moved out of the core by this phase: `IndexLocator` (finding the index database) now lives in Core and is shared by the CLI
  and the MCP server.
- Possible follow-ups, not needed now: publish the package to a feed; a Linux/macOS run of the suite; an MCP tool to refresh the
  index (kept out so the server stays read-only); `--watch`.

### Later ideas (parked)
- Multi-solution or multi-repo index; NuGet dependency metadata; public-API surface diff between versions.
- Analyzer-style queries (for example missing timeouts) built on the same index.

### Consumer-layer ideas (not part of this tool)
Because external symbols are indexed, a consumer can build domain features from ordinary queries, for
example "list every call site of `System.Net.Http.HttpClient` members" or "find subclasses of a gRPC client
base type". Such logic belongs in the consumer's own tooling or an optional separate package, not in the
core indexer.

## 6. Risks and open questions

| Risk or question | Notes and mitigation |
|---|---|
| **Old-style (non-SDK) csproj** | Lower risk for the reference SDK. A syntax-only fallback is plan B for other codebases. |
| **Multi-targeting** | Only one TFM is analyzed; code under `#if NET462` is invisible. Record the TFM and show it in `info`. Needs the F9 fix. |
| **Cross-API project references** | A solution can pull in projects from other API folders; treat them as external and keep them shallow. |
| **Pinned SDK** | `global.json` pins 8.0.426 (now installed here). The loader must honor it (F11). |
| **Restore required** | Detect missing `project.assets.json` per project, report the exact restore command. |
| **Source generators** | Generated code can be missing if a project hasn't been built; document. (The Google SDK checks in generated sources.) |
| **Large solutions** | Process project by project, short-lived compilations; measure in Phase E. |
| **Index trust** | Hash-based `stale` flag is mandatory (Phase D), not optional. |
| **External symbol volume** | Indexing every referenced framework symbol adds rows. Mitigate by inserting stubs only for symbols actually referenced, and measure. |
| **Open: other SDKs after Google?** | Decides how much to invest in the non-SDK csproj fallback. |
| **Open: tool name and repo** | Placeholder `codeindex`. Decide whether it lives in this repo or its own. |
| **Settled: persistent process** | Measured in Phase E (265 ms per call, 4 ms warm); answered in Phase G with an MCP server. |

## 8. Definition of done (overall)

- An agent can, from PowerShell, index a .NET solution and get correct answers for definition, references,
  implementations, callers/callees (including through interfaces), and hierarchy, with small JSON output
  and unambiguous symbol selectors.
- The index is repeatable, staleness-aware, incremental, and safe to delete and rebuild at any time.
- Tests (xUnit) with a rich fixture assert exact results for each extractor and query.
- Verified on `Google.Cloud.Storage.V1` and `Google.Cloud.Speech.V1`.
